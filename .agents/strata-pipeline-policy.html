Strata Development Pipeline

This is the shared policy source for repository-owned Strata workflow skills.

Authority

The canonical repository is Zuriel-Labs/strata and the canonical GitHub Project is the private Zuriel-Labs Strata Project #2. The PM is brimdor. Strata intentionally has no branch protection or repository ruleset; the workflow and evidence remain mandatory even though GitHub does not enforce them server-side.

Approved Issue execution

Repository GitHub Issues are already approved scope. Work, start, initiate, complete, finish, implement, resume and equivalent execution requests all direct the agent to carry the selected Issue through the verified PM Testing handoff. The agent researches, maintains the specification and plan, implements all applicable acceptance criteria, verifies, remediates findings, opens the PR, obtains exact-head CI, deploys and verifies Canary, and supplies numbered PM testing steps without asking for another blueprint, spec, plan, task-list or slice-selection approval. Do not turn agent-generated implementation recommendations into additional PM gates.

Resolve routine choices from approved scope, repository evidence and user instructions. An actual blocker or material decision that those sources cannot resolve still requires input; ask all outstanding questions together and checkpoint the affected task. Preserve explicit scope restrictions, the single-active-Issue invariant and separate approvals for spending or destructive real-data actions. Read-only, discussion-only and plan-only requests retain their stated scope. Generic completion intent does not authorize merge or Production: the exact current-candidate approval remains required at PM Testing.

State flow

  1. After the PM approves a new Issue draft, the agent creates it and moves its Project card to Backlog, open, unassigned, and inactive.
  2. After the PM selects ready work, the agent moves that card to In Progress, assigns only brimdor, and verifies the live Project state before implementation.
  3. The agent implements on issue/<number>-<slug>, validates locally, and opens a PR using Refs #<number>.
  4. The agent completes local QA, including relevant browser interaction testing against a local instance, builds one immutable image from the exact committed PR head, deploys that digest to Canary, and verifies the application runtime and homelab all-green.
  5. Only then does the agent move the Issue to In Review, verify the card, and give the PM numbered, change-specific Canary testing steps.
  6. When the PM reports findings, the agent moves the Issue back to In Progress before remediation. Every change invalidates the earlier candidate and approval.
  7. When the PM explicitly requests a pause, the agent moves the Issue to On Hold and verifies that the active slot is released. When the PM requests resumption and the slot is free, the agent moves it to In Progress and verifies assignment and metadata.
  8. The exact phrase Approved to merge and deploy production, attributable to the PM through the Strata Discord/Issue synchronization record, authorizes squash merge and Production promotion for the recorded candidate.
  9. Production reuses the exact Canary digest without rebuilding. After Production and the full cluster are verified green, the agent resolves every active GitOps image reference, purges obsolete unreferenced Strata image manifests from Zot, and verifies the retained Production digest remains pullable before closing the Issue, moving it to Done, and verifying that the active slot is empty. Release completion does not wait for Zot's delayed background garbage collection or repeat the full runtime and cluster audit solely because manifest cleanup occurred.

Agent-owned Project movement

The PM never has to drag a card, choose a Status value, or repair Project metadata. Human selection, pause/resume requests, review findings, and approval are decision gates; the agent converts each gate into the required GitHub Project mutation and reads the result back immediately.

Candidate identity

A candidate is the tuple of Issue, PR URL, exact PR head commit and tree, immutable Zot digest, and homelab Canary commit. The merge result must have the same Git tree as the approved PR head. Tag or commit identity alone is insufficient.

Deployment ownership

Local testing belongs to the agent, and local browser interaction testing is sufficient to prove application behavior before release. Release images are built from an exact clean Git archive on the local development workstation outside the Kubernetes cluster, target linux/amd64, and are never built ad hoc on a Kubernetes node. Canary is the PM test environment and uses isolated ephemeral SQLite data. Production uses the existing strata-data PVC and backup workload; its data is never copied from Canary. Exact image identity, the one healthy main container, /api/health, zero restarts, Argo CD sync and health, external TLS/route behavior, and whole-homelab green are the Canary runtime gates. Production additionally requires backup freshness, PVC identity, SQLite integrity, and safe schema compatibility. The homelab repository and Gitea master are deployment authority; Argo CD performs reconciliation. Safe non-destructive GitOps rollback is automatic, while destructive data or schema rollback requires PM authorization.

PM testing handoff

Every implementation, remediation, Canary, Production, and completion handoff includes numbered, change-specific PM testing steps even after agent-owned verification passes. The steps identify the environment or URL, prerequisite state, exact actions, expected results, and relevant baseline regression checks. A Canary review handoff is incomplete without these steps.

Every Canary review handoff also presents the exact current-candidate approval phrase in its own standalone fenced code block for direct copying. Inline text alone is not sufficient, and the phrase never authorizes a different candidate.

Completion

An Issue is Done only after its PR is merged, Production runs the approved digest, the Production SQLite database and backup path are verified, the workload is healthy with zero restarts, /api/health passes, Argo CD is Synced and Healthy, the whole homelab is green, obsolete unreferenced Strata image manifests have been purged from Zot, and the retained Production digest remains pullable. Zot's delayed background blob garbage collection is asynchronous and does not block closure, and manifest cleanup alone does not require the full health gates to run again. A merge alone never closes an Issue.
