Strata Access Model

Roles and Permissions

Strata uses platform, workspace, and board roles together. The current implementation enforces access scope and management boundaries server-side through RBAC, with the admin area currently reserved for system_admin users.

Role Definitions

Platform

system_admin

  • Full platform access across all workspaces and boards
  • Open admin panel and manage users, memberships, and roles
  • Create accounts and reset passwords
  • View recent audit activity
Platform

user

  • Base platform role for all non-system administrators
  • No global admin powers on its own
  • Effective access comes from workspace and board memberships
Workspace

workspace_admin

  • Access that workspace and its boards
  • Manage the workspace scope
  • Effectively manage boards inside the same workspace
Workspace

member / guest

  • Access the assigned workspace
  • No workspace management permissions
  • Board-level behavior depends on specific board memberships
Board

board_admin

  • Access and manage the assigned board
  • Can be outranked by a workspace admin or system admin
Board

member / observer / guest

  • Can access the assigned board
  • Cannot manage the board
  • Fine-grained action differences are not fully expanded yet

Important Notes

  • Inheritance: system_admin overrides all scope checks. workspace_admin also inherits management rights for boards inside that workspace.
  • Current admin surface: user creation, editing, role assignment, workspace membership, board membership, password reset, and recent audit visibility are currently restricted to system_admin.
  • Current limitation: board-level member, observer, and guest are mostly differentiated by access scope and management rights today, not yet by a fully separate action matrix like comment-only versus read-only.
  • Important MVP caveat: server-enforced RBAC is strongest today for authentication, admin actions, workspace/board scope visibility, and board-management affordances. Card/list mutation permissions are still more permissive than the final intended model.
  • Source of truth: server-side enforcement lives in server/src/rbac/permissions.ts, server/src/rbac/policies.ts, and protected routes under server/src/routes/.
