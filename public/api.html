Make your first request

  1. Create an API key in API Connections. Choose My account and Read account.
  2. Use your Strata deployment’s HTTPS origin. The supported API is under /api/v1; OAuth and browser setup use separate paths.
  3. Start with GET /api/v1/me. Its request template shows where to pass your key. Configure the real key through your client’s protected credential store.

Connect an agent

  1. In Strata, open your account menu, then API Connections. Name the key, choose resources and individual actions, select an expiration, and review before creating it. Manage multiple keys under Manage API keys. The secret appears once. Save it in your client’s protected credential storage.
  2. Send the secret as an Authorization: Bearer header to /api/v1 over HTTPS. Query-string credentials and browser-session fallback are unsupported. An API credential cannot approve or create another credential.
  3. Use /api/v1/me for account-only access; use /api/v1/state for the scoped Web UI snapshot with both content:read and account:read.
  4. Return to API Connections to inspect scope, resources, expiry and last use, or revoke a connection immediately. Revocation covers every token in its family. Password changes and account disablement revoke all that user’s connections.

On the Permissions step, Select all shown checks only the actions that match your filters. Role preset fills the chosen role and lower roles for your selected resources. Personal account actions have their own preset. Review the final list before creating the key.

Service accounts

Open Administration → Service Accounts to create an agent with a stable ID, unique username and its own API key. Use Edit assignments for its workspace or board administration and Board Members to add it as a member or observer. Board members can be selected for card and automation assignments. The key authenticates the agent under its own ID and limits what it can do. The owner’s current authority also applies. The agent cannot sign in to the browser or use personal account actions. Changing administrative assignments or transferring ownership revokes the previous key. Transfer preserves the username and ID, and keeps only access available to the new owner.

Device Authorization for headless clients

Discover endpoints at OAuth authorization server metadata. Public clients have no shared secret. Built-in client_id is strata-cli; registered client IDs also support device flow.

  1. POST /api/oauth/device/authorization with form fields client_id, space-separated scope, and space-separated resource.
  2. Display the returned user_code and verification_uri. Open that exact Strata origin in the user’s browser. The user must compare the code, review permissions, resources and the displayed connection expiry (at most 30 days from request creation), then explicitly approve or deny. Never ask for the user’s password, recovery key or browser cookies.
  3. Wait at least interval seconds (initially 5). POST /api/oauth/token with grant_type=urn:ietf:params:oauth:grant-type:device_code, the same client_id and private device_code.
  4. On authorization_pending, keep waiting. On slow_down, add 5 seconds to every subsequent polling interval. On network timeout, increase delay with exponential backoff. Never overlap polls. Stop on access_denied, expired_token or invalid_grant. The request expires after 10 minutes.
  5. On success, store access_token and refresh_token securely. The access token lasts at most 600 seconds. POST grant_type=refresh_token, client_id and refresh_token to rotate. Atomically replace stored tokens before another request. Old refresh-token reuse revokes the entire connection, including the latest access token. Scope, resources and the original grant expiry cannot expand on renewal.
  6. Cancel by POSTing client_id and private device_code to /api/oauth/device/cancel. Revoke an issued connection by POSTing client_id and a bound token to /api/oauth/revoke. Both operations are idempotent.

Interactive clients: authorization code + PKCE

Register a named public client and its exact callback URL in Approved Apps. Registration requires a browser account and returns a public client ID, never a client secret. Use HTTPS callbacks or an exact loopback IP URL (http://127.0.0.1:port/path or IPv6 loopback). No wildcard, userinfo, query or fragment is allowed; the port is part of the registered exact URL.

Generate a fresh cryptographically random state (at least 128 bits) and 43–128-character PKCE verifier for each attempt. Send response_type=code, client_id, redirect_uri, scope, resource, state, code_challenge=BASE64URL(SHA256(verifier)), code_challenge_method=S256 to /api/oauth/authorize. After browser approval, verify the returned state and callback origin/path before redeeming. POST grant_type=authorization_code, client_id, exact redirect_uri, code and code_verifier to the token endpoint. The code expires after 60 seconds and is redeemable once. Denial returns access_denied with the original state. Do not use implicit or password grants.

Scopes, resources & roles

Approved scopes never replace current authorization. Every API call and renewal reloads the active account, current memberships and roles, intersects the authority captured at approval, then applies approved resources and the shared domain policy. Later promotion cannot enlarge an existing connection. Removed membership stops access immediately; an observer cannot write even if an older credential contains a write scope.

ScopeOperations
content:readRead authorized content, collections, navigation and automation.
content:writeCreate/edit/move/duplicate cards, comments and reviewed copy/move operations. Current role must also permit each operation.
content:manageManage workspaces, boards, lists, labels, collections, lifecycle and automation. Permanent deletion also requires content:write for preview/commit and typed DELETE confirmation.
administration:read / writeRead or manage users and board membership/invitations within current administrative authority. Platform account mutations require the platform resource and current System Admin.
account:read / writeRead your own account / update profile, preferences, navigation, notifications and accept an in-scope invitation.
account:securityGenerate your recovery key or change your password with current-password verification. Password change revokes this connection too.

Resources: account (account scopes only, no content), board:ID, workspace:ID (authorized boards in that workspace), or platform (System Admin only). Workspace scope does not grant membership in other boards. Cross-resource copies, moves, defaults and assignments validate both source and destination. A board-scoped credential cannot manage its parent workspace.

Personal keys expire within 1, 7, 30, 60, 90, or 180 days. OAuth connections expire at most 30 days after the authorization request began. Up to 100 active connections and 100 public client registrations per account. A revoked or expired connection cannot be restored.

Common workflows

The versioned operation inventory publishes method, path, shared request schema, required scopes, resource policy, query parameters and responses for every server-backed UI operation. Runtime routes reuse the existing domain routers. The route parity test compares published operations with Express route registration.

  • Read: workspaces, boards, lists, cards, checklists, comments, attachments, labels, automation, notifications, users, memberships, collections and account state. Search, filters, board views, card-detail rendering and drag/drop presentation are client views over these resources; state changes use the listed operations.
  • Content: create/rename/configure, card fields and rich text, comments, movement, duplication, sorting, labels with expected label revision, collection membership, list colors/collapse, archive/restore, close/reopen and templates.
  • Copy/move/delete: first POST /api/v1/content-operations/preview. Review the returned planHash, impact, mappings and blockers. Commit identical inputs and planHash with a UUID Idempotency-Key; deletion additionally requires confirmation=DELETE. Revision or graph changes require a new preview. Reuse a key only for the same request and connection. Legacy direct DELETE content endpoints deliberately return PREVIEW_REQUIRED.
  • Administration: scoped user/resource pages, account creation/updates/deletion, recovery keys, board memberships, invitation creation/revocation/acceptance and platform label policy. System Admin-only operations remain System Admin-only.
  • Browser account lifecycle: initial bootstrap, sign-in and recovery-key consumption establish or recover a browser account. They are not password grants for agents. Use Device Authorization or PKCE for agent credentials. Browser connection management requires same-origin requests with X-Strata-Intent: connections and an explicit approval.

Read a workspace incrementally

  1. Choose an approved workspace or board with read access. Call GET /api/v1/workspaces to discover visible workspace IDs.
  2. Use GET /api/v1/boards with workspaceId=YOUR_WORKSPACE_ID&limit=25. Pass the returned nextCursor as cursor alongside the same filters and connection. Stop at null.
  3. Use a returned board ID as boardId in GET /api/v1/cards to page through visible cards.

Commit a reviewed content change

Use POST /api/v1/content-operations/preview to review impact and get a plan hash. Then use POST /api/v1/content-operations with the matching inputs, plan hash, and a fresh idempotency key. A changed plan requires a fresh preview.

Pagination & concurrency

GET resource collections accept limit (1–100, default 25), cursor, boardId and workspaceId. Responses contain items and nextCursor (null at the end). Treat cursors as opaque, preserve filters and use the same connection. Empty authorized results reveal no foreign content. Administration and invitation pages use page/pageSize with published maximums and return page metadata; personal navigation uses limit up to 50 and its own cursor. Snapshot endpoints intentionally return the complete approved application state; prefer collection pages for incremental clients.

Use expectedRevision / expectedUpdatedAt / expectedLabelsRevision where the operation schema requires them. For 409, reload and reconcile; never overwrite a changed resource by guessing a revision. Rich text and attachment inputs pass the same sanitization and validation as the Web UI.

Errors, limits & retries

Versioned API errors return code and message. OAuth protocol errors return error and error_description; OAuth rate limits use a separate 429 response. A 401 requires a new valid credential. A 403 requires corrected approved access or current role; retrying cannot grant permission. A 404 does not distinguish hidden from missing content. A 400 requires corrected input. A 409 requires fresh state/preview. Unknown server failures return a generic message without storage paths or raw request data.

Strata application limits in this build: 120 requests per connection per minute and 600 per IP per minute. OAuth: 60 requests per IP per minute, including token polling; device/code starts and key/client creation: 10 per IP per minute. Consent code lookup: 5 attempts per IP per 10 minutes; decisions: 10 per minute. 429 includes Retry-After seconds; wait and apply jitter. These windows are set in the server code and stored in the database. A deployment’s edge may apply additional controls. Device polling has its separate increasing interval. Do not retry non-idempotent writes blindly after timeouts or 5xx; reconcile state first or replay the same content-operation idempotency key.

Credential handling

Never paste credentials into chat, model prompts, source code, issue reports, shell arguments, URLs, screenshots or logs. Authorization headers and token endpoint request/response bodies must be redacted by clients, reverse proxies and telemetry.

Use the OS credential store (Keychain, Credential Manager or Secret Service), or an encrypted secret manager. If unavailable, use a dedicated user-only directory (0700) and token file (0600), reject symlinks, replace atomically, and encrypt backups. Never put credentials in browser localStorage or shared workspaces. Keep access tokens in memory when practical. Serialize renewal and commit the rotated refresh token before use; after a crash with uncertain rotation, reauthorize rather than replaying an older token. Delete stored tokens after denial, expiry or revocation.

Strata restricts its SQLite file to the service user (0600) and stores only SHA-256 token/code digests; raw personal keys are returned once. Versioned bearer operations do not issue browser session cookies. Audit records attribute domain changes to the issuing user, connection ID and operation template, and record approval, token issuance/rotation and revocation using safe identifiers. Secrets and private device codes are excluded.
