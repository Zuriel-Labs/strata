1. Foundation and scope

Constitution

Follow the repository operating standard and pipeline policy. Keep private access as the effective baseline. Administration does not imply collaboration membership. Membership in one board does not disclose its siblings. Validate requests with Zod, enforce server policy, and retain safe audit evidence. Reuse completed #1–4, #24, #29 and #30.

Specification

Serve signed-in System Administrators, scoped Workspace/Board Administrators, Members and Observers, plus anonymous login/recovery users. Cover home, workspace switching, recents/stars, profile/theme/defaults, keyboard navigation, identity/recovery/logout, existing-account membership, invitation lifecycle and visibility/link policy. Produce entities, API errors, permissions, audit effects, migrations, recovery, ordered tasks and executable test oracles.

Analysis

The existing hierarchy and reconciliation code provide a usable foundation. The smallest first application slice is preference clearing and workspace/board-pair validation: both have concrete source evidence and need no new disclosure model. Recovery concurrency and session lifecycle are the next security-sensitive contract. Personal navigation storage, invitation lifecycle and public sharing require separate bounded slices; do not turn this XL aggregate into one implementation PR.

Boundaries

  • Always: preserve existing roles and data, distinguish source facts from proposals, keep unknown runtime behavior unknown, and map every original criterion below.
  • Approval gates: approve the blueprint and select an implementation slice before application changes; resolve applicable D1–D4 decisions before enabling their behaviors. Merge/Production approval remains candidate-specific.
  • Excluded: account self-registration, email delivery, SSO/SCIM, groups, billing, paid AI, native applications, offline editing, full search redesign, card-content/lifecycle implementation, and any deployment in this blueprint batch.
  • Dependencies: none for this blueprint. #41 consumes this access contract; #47 and #52 consume it through their declared sequence. Recheck board-movement compatibility with #41 before implementation. Notification delivery belongs to #52; it is not a prerequisite to writing this blueprint.

4. Observable requirements

  1. R1 — Preserve baseline. Username login, recovery keys, profile/theme, scoped administration, membership and last-admin protection retain existing behavior except explicitly selected fixes. Sources E1–E5, E10–E11.
  2. R2 — Valid navigation. Selected board belongs to the selected accessible workspace. Removed/denied destinations expose no board/card metadata. Empty home, empty workspace, no history, stale link, network failure and session expiry have distinct recoverable states. W1–W3, W11.
  3. R3 — Private personal metadata. Future recent/starred records belong to the authenticated account, grant no access and are filtered on each server read. No client-supplied user ID selects another account's metadata. W3–W4; D1.
  4. R4 — Faithful preference patch. Omitted fields preserve values; explicit null clears defaults; inaccessible/nonmatching defaults reject without partial theme/default/audit-success changes. W6.
  5. R5 — Keyboard and focus. Discoverable navigation works outside editable targets, ignores IME composition, has visible focus and labels, traps focus in modal dialogs and returns it to a surviving trigger. W5/W8.
  6. R6 — Account/session recovery. Revoked sessions cannot resume. A valid recovery key permits one committed reset even with concurrent requests; failure changes no credentials. Successful recovery revokes every prior session. Password change rotates the current session and invalidates others under the proposed contract. W9–W11.
  7. R7 — Independent administration. System Administrators alone create accounts/manage admin grants. Scoped administrators manage only existing-account board memberships in their effective scope. Removing board access preserves unrelated grants/accounts and updates derived membership. W12.
  8. R8 — Invitation lifecycle. Conditional invitation acceptance is bound to its target and board, validates current issuer authority, expires/revokes safely, and is idempotent without upgrading an existing role. Never reuse an account recovery credential as a board invitation. W13; D2.
  9. R9 — Disclosure and Observer policy. Stored visibility alone creates no grant. Any future workspace/public/read-link access requires D3, a minimal read projection, identical direct-API enforcement and non-revivable revocation. Observer membership/read links grant no board-domain mutation rights; own profile/personal navigation metadata remains separate. G9 is an existing exception to remedy, not verified conformance. W14–W15.
  10. R10 — Audit and integrity. Security mutations commit state, session invalidation and audit atomically. Denied writes leave domain state unchanged, with safe denial evidence. Never retain raw passwords, keys, bearer links, cookies or session IDs in reports/logs/audit. W9–W15.
  11. R11 — Notification boundary. Define own in-app preference storage separately from notification ownership and event delivery. New delivery/provider behavior waits for #52 and applicable explicit approval. W7; D4.
  12. R12 — Evidence and safe delivery. Every W1–W15 disposition and original criterion has source/task/scenario coverage. New fields/endpoints below remain proposals until selected. Rehearse additive migrations and rollback; run required exact-source validation before any implementation release.

6. Concrete contracts

Existing endpoints are identified explicitly. All new entities, paths, field limits, status codes and algorithm choices in this section are proposals for later selected implementation, not claims of shipped behavior.

C1 — Preserve identity and safe session projections

Keep existing POST /api/auth/login body { username, password }, GET /api/auth/session, POST /api/auth/logout → 204, PATCH /api/auth/profile body { name, initials, color }, and authenticated/password-change-required response variants. Continue deriving the actor from the session cookie. Do not expose password/key hashes or session IDs in payloads. Account identifiers remain usernames; recovery has no email dependency. E2–E3.

Existing sessions store id, user_id, expires_at, created_at, last_seen_at; default lifetime is 24 hours. Preserve that lifetime in this work. On confirmed 401, clear private app state and overlays, then offer login. On transport failure show retry and do not describe the account as revoked. No design promises to erase content already seen or saved by a former authorized user.

C2 — Preference patch, existing endpoint

PATCH /api/auth/preferences returns 200 { user }. Fields remain themePreference?: "dark" | "light", defaultWorkspaceId?: UUID | null, defaultBoardId?: UUID | null. Pass explicit null through the client. A non-null board requires a non-null workspace in the same request, the board must actually belong to that workspace, and both must be accessible. Clearing workspace clears board. Changing workspace with omitted board clears the old board. Omitted unrelated fields preserve saved values. Validate the complete resulting selection before one write and its success audit.

{ "themePreference": "dark", "defaultWorkspaceId": null, "defaultBoardId": null }

Proposed stable errors, preserving message: 400 PREFERENCES_INVALID for schema failure; 400 DEFAULT_SELECTION_INVALID for inaccessible/nonmatching IDs without distinguishing which inaccessible resource exists; 401 for no session. Rejected requests change neither theme nor defaults and emit no success audit. Successful updates keep auth.preferences_update with non-secret resulting identifiers.

C3 — Recovery and password atomicity, existing endpoints

Keep POST /api/auth/recovery-key/consume body { username, recoveryKey, newPassword, confirmPassword } and success 200 { newRecoveryKey }. Preserve supported legacy hash verification in auth/recovery-keys.ts. After asynchronous password/key verification, one synchronous SQLite transaction must re-read and conditionally consume the same key version/hash, update the password, install the replacement key, revoke all old sessions and write auth.recovery_consume. Exactly one concurrent request commits; subsequent use returns a generic 401 RECOVERY_INVALID. Inactive accounts fail without changing credentials.

No raw key is an audit field. Do not persist an idempotency response containing a replacement key. If a successful response is lost, the old key remains consumed; use the existing System Administrator recovery reissue path. No automatic sign-in follows anonymous recovery. For POST /api/auth/password/change, preserve the body and 204 response, but atomically invalidate prior sessions and issue a fresh current-session cookie; forced rotation remains compatible. Existing authorization changes retain immediate next-request invalidation. Rollback of a credential change never restores old keys or revoked sessions.

C4 — Personal navigation, proposed additive model

Proposed user_board_navigation: composite primary key (user_id, board_id); foreign keys cascade only when that account/board is deleted; last_visited_at TEXT NULL, starred INTEGER NOT NULL DEFAULT 0 CHECK (starred IN (0,1)), starred_at TEXT NULL. Timestamp authority is the server. Index (user_id, last_visited_at DESC, board_id). No copies of board titles, credentials or visibility grants. Retain at most 50 recent references per account; this is a proposed Strata bound, not a Trello quota. Starred pagination is bounded separately.

  • GET /api/auth/navigation?kind=recent|starred&limit=1..50&cursor=... → 200 { items: [{ boardId, workspaceId, title, color, starred, lastVisitedAt }], nextCursor }. Reapply current access before projecting metadata. Recent order: timestamp descending then board ID; star order: starred timestamp descending then board ID. Validate opaque cursors against the current actor; invalid input → 400 NAVIGATION_INVALID.
  • PUT /api/auth/navigation/boards/:boardId/visit, empty body → 204 after successful authorized board selection. Repeated calls upsert one reference; client never provides a user ID or timestamp. Inaccessible/missing target → uniform 404 DESTINATION_UNAVAILABLE; record no visit.
  • PUT /api/auth/navigation/boards/:boardId/star body { starred: boolean } → 200 { boardId, starred }; set semantics make retry idempotent. No shared boards.starred write. D1 decides legacy compatibility/migration. A separately selected G9 fix must require effective Board Administrator authority for the legacy shared write, returning 403 without state change for a plain Member/Observer; preserve shared values and add a safe success audit. Own personal stars remain available to every authorized role.

Revocation filters records immediately on the next authorized server read; a later maintenance/delete operation may remove stale references without ever returning them. A local active board missing from the refreshed projection clears its card selection and content. Existing Header/reconciler/store patterns should be reused. Do not mount administrative Management controls for Members just to expose personal navigation.

C5 — Invitation lifecycle, conditional on D2

Proposed board_invitations: id UUID, board_id, target_user_id for an existing account, role member|observer, token_hash unique, issuer_user_id, created_at, expires_at, accepted_at NULL, revoked_at NULL. No external email identity, direct workspace-membership row or administrative role. Recipient identity remains bound even if the account username changes. Preserve minimal terminal metadata; a proposed 30-day terminal-record retention needs D2 approval and cannot delete audit history.

  • POST /api/admin/boards/:boardId/invitations body { targetUserId, role, expiresAt } → 201 { invitation: { id, boardId, targetUserId, role, expiresAt, status: "pending" }, token }. Proposed expiry: future UTC instant at most seven days away. Return the token only once; no automatic external transmission.
  • GET /api/admin/boards/:boardId/invitations?status=pending&page=1&pageSize=1..50 → bounded metadata only. DELETE /api/admin/boards/:boardId/invitations/:id → idempotent 204 revocation; it does not remove an already accepted membership.
  • POST /api/auth/board-invitations/accept body { token } → 200 { boardId, membershipRole, alreadyAccepted }. Require the bound active signed-in recipient and current issuer authority. One transaction checks expiry/revocation, inserts at most one membership, marks acceptance, revokes target sessions and writes the audit; rotate the current cookie for a self-accepting recipient.

Retry by the same recipient returns the existing acceptance only if the membership remains; it never recreates membership after an administrator removed it. Existing membership is not upgraded or downgraded by an invite: return 409 MEMBERSHIP_ALREADY_EXISTS. Expired/revoked/unknown/wrong-recipient tokens share 404 INVITATION_UNAVAILABLE; malformed bodies use 400, anonymous requests 401, forbidden issuance/revocation 403. Failed acceptance writes no membership. Audit board.invitation_create|accept|revoke includes actor, target, board, invitation ID and outcome, never the token. Current account-activation/recovery links retain their distinct format and behavior.

C6 — Visibility and read links, conditional design only

Current policy: visibility values are metadata; grants/memberships determine access. Keep all current values and behavior until D3 approves a semantic migration. A board guest remains a normal scoped account relationship, not a new global role. Do not copy Trello's direct workspace membership model or Observer commenting capability.

Conditional proposal: a visibility version field distinguishes legacy metadata from newly approved semantics. A future workspace-visible board may be read by a derived workspace member, but membership in one board must not silently enable this; every existing board stays on the legacy policy until individually confirmed. “Public” requires explicit effective-administrator confirmation of the projected fields. Both changes require D3 because they broaden disclosure.

Proposed board_read_links: id, board_id, issuer_user_id, token_hash UNIQUE, created_at, expires_at, revoked_at, with fixed permission=read. Proposed POST /api/admin/boards/:boardId/read-links body { expiresAt } returns 201 { id, token, expiresAt }; delete by ID returns 204 and permanently marks revocation. A separate GET /api/shared/boards/:boardId with bearer authorization returns only { board: { id, title, color }, lists: [{ id, title, position }], cards: [{ id, listId, title, description, position }] } after validating the live token, issuer authority, current board policy and expiry. No cookies or grants are created. Reject mutations and never reuse this token on internal session endpoints.

Exclude members/usernames, comments/authors, attachments/URLs, automation configuration, notifications, audit and archived content from that proposed projection. D3 must explicitly approve even the listed card content before implementation. Return uniform 404 SHARE_UNAVAILABLE for missing/expired/revoked/disabled links and 400 for malformed input; use Cache-Control: no-store and no raw-token logs/referrers. Subsequent reads fail immediately after revocation commits; offline copies/screenshots cannot be recalled. Issuer re-grant never revives a revoked token. Sharing audit records metadata only. Public anonymous routes, rate controls and route-level security review are mandatory before enabling any disclosure.

C7 — Notification preference interface, delivery deferred

Proposed user_notification_preferences(user_id PRIMARY KEY, in_app_enabled BOOLEAN NOT NULL DEFAULT 1, updated_at). Own GET/PATCH /api/auth/notification-preferences with { inAppEnabled: boolean } → 200 same shape, 400 invalid, 401 anonymous; actor comes from session. Store only intent after D4. #52 specifies which events honor that intent and their retry/ownership behavior. Do not hide mandatory account-security information, mutate other users' notifications or introduce email, push, webhook or paid-provider calls. Do not expose an inert setting before its delivery contract exists.

C8 — Migration, rollback and coding conventions

G3 preference fixes and G4 keyboard fixes need no schema migration. C4/C5/C7 are additive table proposals; C6 adds explicit versioning rather than reinterpreting historical strings. Rehearse on synthetic pre-change databases: migrate twice, compare user/grant/content/audit counts and foreign-key integrity, preserve existing shared stars, then verify old/new reader compatibility. Migration failure rolls back the transaction. Membership and security operations must include safe audit and session effects in their transaction. Revoke affected invitations/read links when scope or issuer authority is removed; never reactivate them on re-grant.

Rollback disables new entry points/read-link grants and returns to the known-good application image while retaining additive data. It must not restore a consumed key, session or revoked link. No destructive down-migration, drop of legacy stars, account deletion or data restoration is authorized by this blueprint. #41 owns movement/deletion mechanics and must consume these revocation/ownership invariants.

Use strict TypeScript, named ES-module exports, import type, existing Express/Zod early-return validation and house UI primitives. Keep policy, projection and persistence concerns separate; use the existing audit helper. A request body is data, never authority.

const parsed = preferencesUpdateSchema.safeParse(request.body);
if (!parsed.success) {
  response.status(400).json({ code: 'PREFERENCES_INVALID', message: 'Invalid preferences payload.' });
  return;

Later application implementation gates

  1. Read the current source and live single-active pipeline; record the selected slice and acceptance criteria. Work in an isolated branch from current main.
  2. Write one behavior test; run it red for the intended gap; implement minimally; run green; refactor only while green. Preserve existing auth/RBAC/audit regressions.
  3. Run the focused Vitest file, for example npm run test -- server/tests/auth-routes.test.ts for T2/T3. Run npm run typecheck, npm run lint, npm run test, npm run build, relevant npm run test:e2e -- tests/e2e/layered-access.spec.ts and complete npm run check before an implementation handoff. Inspect every exit status; list any unrun gate explicitly.
  4. Rehearse applicable migrations with synthetic data, review privacy/security/dependencies, and test affected local browser journeys at desktop/tablet/phone widths with keyboard/focus/error/revocation checks. Record skipped browser/assistive-technology coverage honestly.
  5. Stop/reap owned test processes and remove only the task's disposable databases, packages, caches, screenshots, recordings and app images. Preserve source, real data, credentials and unrelated resources. Retain compact sanitized evidence.
  6. Commit intended files, use Refs #39 in the PR, require exact-head Quality / verify, and follow the repository review/release skills. No auto-close keyword. This blueprint itself authorizes no Canary or Production deployment.
