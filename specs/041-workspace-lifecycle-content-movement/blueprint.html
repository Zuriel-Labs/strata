1. Foundation and boundaries

Constitution

Follow AGENTS.md and the pipeline policy. Preserve independent administration, board-rooted membership, effective private access, safe audit history and existing data. Use strict Zod boundaries, centralized server policies and SQLite transactions. No new dependencies are proposed.

Specification

Users are System Administrators, scoped Workspace/Board Administrators, Members and Observers. Specify workspace/board/list lifecycle, independent copies/templates, collections, personal versus shared stars, cross-board transfers, reversible archive and destructive-action safeguards. Success means every original workflow has a disposition, concrete contract and executable test oracle, with policy gates visible before implementation.

The current schema and transactional duplication/sort helpers are reusable. 4. Observable requirements

  1. R1 — Atomic mutation. Commit domain data, positions, access/session effects, audit and local automation effects together. Injected failure leaves all unchanged. Strictly validate strings, IDs, options, revisions and payload size; reuse existing name/content limits where defined.
  2. R2 — Access follows current hierarchy. Collections, templates, colors, stars and provenance grant no authority. Re-evaluate source and destination inside the write transaction; derived workspace context is recalculated. Revoked actors cannot retain access through stale session projections.
  3. R3 — Independent copy. Allocate new identities for every copied object and nested mutable object. Preserve only selected allowed fields; never copy memberships, grants, invitations, credentials, personal navigation or another user's watching state. No operation occurs before confirmation.
  4. R4 — Safe transfer. Move retains resource identity, rewrites all affected parent references atomically, reconciles members/labels/fields explicitly and warns about audience changes. No silent label-name matching, role grants or attachment disclosure.
  5. R5 — Deterministic ordering and retry. Use all active siblings, stable position/ID ties, contiguous resulting positions and revision checks. Retry of one committed operation returns the same result without another object, audit, notification or local automation effect.
  6. R6 — Reversible lifecycle. Close preserves content, memberships and explicit grants; parent state blocks ordinary mutation. Restore never opens a parent or independently archived child. Do not manufacture unavailable pre-migration archive provenance.
  7. R7 — Presentation ownership. Collections and colors are shared administrative metadata; collapse is personal and available to authorized readers including Observers. No presentation action silently changes ordering/content or another user's state.
  8. R8 — Explicit destruction. Preview exact descendant/reference effects; reconfirm freshness/authority server-side, require closed/archived state and typed confirmation, and retain sanitized audit/tombstone metadata. No automatic deletion, unapproved retention deadline or undo promise after permanent deletion.
  9. R9 — Shared attachment safety. Fresh attachment reference IDs can share immutable storage only through authorized, separately tracked references. Removing one reference never deletes another's bytes. No external fetch/upload or attachment authorization bypass during copy.
  10. R10 — Recoverable accessible UI. New surfaces meet U1; session loss clears private content, network failure retains draft, cancel is side-effect free, keyboard/focus and narrow layouts are verified separately from API tests.

All C1–C7 additions are proposed, not implemented endpoints. Preserve current APIs until an approved compatibility change migrates all clients. New bodies use strict Zod objects; reject unknown fields, duplicate maps, dangling IDs, invalid enums and stale revisions. New resource names trim to 1–200 characters; descriptions reuse existing validated rich text. IDs are opaque strings compatible with legacy IDs; new IDs use randomUUID(). Page size 1–100, default 25, stable cursor order. The existing board label policy (default 12, ceiling 100, grandfathering, labelsRevision) remains authoritative.

C1 — Lifecycle, provenance and presentation entities

  • Add workspaces.lifecycle_state and boards.lifecycle_state: active/closed, default active; closed_at, closed_by_user_id nullable; revision integer ≥0 default 0. Add list/card revision counters for affected writes. Keep existing archived flags.
  • Add boards.is_template boolean default false; source_template_id nullable metadata without granting source access; source_template_revision nullable integer. Return provenance only if source remains readable; hide inaccessible titles/IDs in user projections.
  • Add cards.archived_by_list_id nullable reference (ON DELETE SET NULL). On list archive set it only for previously active children; on restore clear archived only for children marked by that list. Already archived children stay archived. Legacy ambiguous archives have null provenance and require explicit per-card restore after parent restore.
  • Add board_collections(id,workspace_id,name,revision,created_at), unique normalized name per workspace; board_collection_items(collection_id,board_id) unique pair. Enforce same-workspace ownership in mutation transaction. Board transfer removes source collection links; never copies collection access.
  • Add nullable shared lists.color constrained to existing palette tokens. Add user_list_preferences(user_id,list_id,collapsed,updated_at), primary key user/list, cascading on user/list deletion. Personal rows filtered by current access.
  • Effective state is active only when resource and every ancestor are active/unarchived. Closing a parent does not overwrite child state. Read-only closed views remain authorized; interactive writes, scheduled/realtime automation and invitation acceptance must reject inactive ancestors.

C2 — Operation plan, revisions and receipts

Two-stage interaction: read-only plan then explicit commit. POST /api/content-operations/preview body contains kind (board_copy, board_move, list_copy, list_move, card_copy, card_move, delete), sourceId, optional destination workspace/board/list and nonnegative position, explicit keep/reset options and label/member/field maps. Response 200: {planHash,sourceRevision,destinationRevision,counts,warnings,unresolvedMappings,expiresAt}; no copied rows, audit-success or automation. Preview includes only authorized metadata. Plan validity: five minutes; authorization and complete affected-state fingerprint are checked again at commit.

POST /api/content-operations requires Idempotency-Key UUID and the full preview inputs plus planHash. Success 201 for copies, 200 for moves/deletion: {operationId,resultIds,revisions,counts}. Retry returns the original status/result with a replay indicator after current authorization check. Stale source/destination/descendant state requires a new preview, not silent remapping.

Proposed content_operations(id,actor_user_id,idempotency_key,request_hash,kind,result_json,http_status,committed_at), unique actor/key, and content_operation_effects(operation_id,rule_id,subject_id,effect_kind) unique tuple. Transaction: lock for write; resolve current authorization/state; check receipt/key hash; compare plan/revisions; mutate all rows; apply existing local automation with deduplicated effect keys; write audit and minimal result receipt; commit. Any failure rolls back everything, including the receipt. Unknown external effects are excluded; never claim exactly-once remote delivery. A reused key with another request returns 409 OPERATION_KEY_CONFLICT. Receipts retain minimal metadata indefinitely initially; no automatic cleanup without an explicit retention decision.

Every existing path capable of changing plan inputs must advance revisions or contribute to the commit fingerprint, including label edits, JSON card fields, grants, memberships, invitations and automation configuration. Recheck inside the transaction even when revisions match. Do not introduce an operation framework for independent T1 fixes; C2 is shared only by approved copy/transfer/destruction work.

C3 — Copy and template profile

Board copy input selects destination workspace, title, color and keep:{cards,descriptions,checklists,checklistCompletion,labels,dueDates,dueCompletion,attachments}. List/card copy additionally supplies destination board/list and position. Boolean fields are explicit; omitted options use the approved profile, never a hidden carry-over from another dialog. Template creation reuses board copy at a pinned source revision; instances have no live mutable relationship to the template.

Proposed default: active lists/cards, descriptions, labels and checklists retained; checklist completion reset; dates, due completion and attachments off; comments/history/memberships/grants/invitations/member assignments/watching/personal stars/recents/automations never inherited. New board gets an explicit Board Admin grant for its creator, without a collaboration membership. New IDs for boards/lists/cards/labels/checklists/items/attachment references and fresh created activity. Existing POST /api/cards/:id/duplicate remains backward compatible with #17, including its present date/checklist/member rules; the new configurable Copy action is separately labeled.

Opt-in attachments require C7-safe references; until #47 implements authorization-backed reference ownership, preview returns 409 ATTACHMENT_CONTRACT_UNAVAILABLE for selected attachments rather than copying unsafe URLs. Unknown/custom fields produce unresolved mappings and block commit until #47 defines them. Copying automation rules is deferred; destination's existing local card_created rules execute once per created card, inside the transaction, with results shown in the receipt. Board-copy destination has no copied rules. Templates retain private grants; conversion hides collaboration controls without deleting comments/history.

C4 — Transfer and cross-board reconciliation

Board parent transfer retains board/list/card IDs, explicit Board Admin grants and collaboration memberships. Atomically update workspace parent, derived memberships/session projections, defaults that no longer form valid workspace/board pairs, source collection links and issuer-authority invitation revocation. Compute before/after effective reader/admin sets; show newly gaining/losing audience to an actor authorized to inspect it. Invalidate sessions for affected actors before success; current actor may need reauthentication. Source-only inherited administrators lose authority immediately. Destination inherited administrators gain it only under approved D2.

List/card transfer rewrites both list/card parent fields, including every descendant card.board_id. Retain IDs and content on move. Label map uses exact source ID → authorized destination ID or explicit drop; member map retains only active destination Members (not Observers or admins without membership). No membership grants or label creation by name. Fields without mappings block or require explicit drop approval. History/comments retained on move under D2; no copied prior history on copy. Watching resets if its current legacy aggregate cannot be attributed safely.

Cross-board notification records are removed for the moved card if tied to the old audience; do not rewrite them into unauthorized destination notifications. Source automation references to moved list IDs are disabled/cleared with attributable audit; no source rule follows the object into another board. Run destination card_moved once per moved card and no card_created event for move. Bulk list movement includes archived descendants but does not activate or run automation for them; a selected archived source card/list requires restore first. Source/destination active order compacts atomically. Destination rule execution can alter the final position; response returns authoritative final state. No external notifications or provider calls.

C5 — Lifecycle and presentation routes

  • POST /api/workspaces/:id/close, /reopen; equivalent /api/boards/:id/close, /reopen: {expectedRevision}; 200 {id,lifecycleState,revision}. Reopen in current workspace only, never implicit transfer. Same-state retry is a no-op with no duplicate audit. State and success audit share a transaction. Board/workspace close pauses scheduled effects; it does not delete rules/grants/memberships. Invitation acceptance is blocked while closed, not silently revoked merely by closure.
  • Existing list archive/restore and card archived update preserve URLs but gain transactional provenance and active-parent enforcement. During an approved API compatibility change, accept expectedRevision consistently and migrate all service callers. Archived/closed listing adds bounded state filters to authorized projections; broad bootstrap must not load closed content into active views/search.
  • PUT /api/boards/:id/template {isTemplate,expectedRevision} returns 200 updated board. Read-only consumer state does not replace RBAC; only administrators may change template content.
  • GET/POST /api/workspaces/:id/collections; POST {name} →201 collection; PATCH /api/collections/:id {name,expectedRevision} →200; DELETE /api/collections/:id with revision →204, removes grouping only; PUT /api/collections/:id/boards/:boardId and DELETE →204, idempotent. Lists are access-filtered; suppress empty unauthorized collection metadata and hidden-board counts.
  • PATCH /api/lists/:id/presentation {color,expectedRevision} →200; PUT /api/auth/list-preferences/:id {collapsed} →200 own preference. Color accepts null to clear. No userId accepted. Personal collapse does not increment domain content revision.

C6 — Deletion preview, tombstone and retention

Proposed D3: archive/close retained indefinitely with no purge job. Only archived cards/lists and closed boards/workspaces qualify for permanent deletion. C2 preview lists direct/descendant counts by type, preserved audits, removed notifications/navigation/default references, invitations/grants/memberships, attachment reference count and retained shared blobs. Partial knowledge blocks preview approval. No payload content or token goes into the receipt.

Commit adds confirmation:"DELETE", matching planHash/revisions and idempotency key. Recheck all descendants, current authority and state. Permanently delete graph rows and owned references in one transaction; clear dangling defaults, card notifications and automation references; revoke affected sessions; preserve audit_events. Return {operationId,resultIds:[],counts,tombstoneId}. Existing direct DELETE APIs must enforce equivalent preview/confirmation policy after approved coordinated client migration; do not leave bypasses.

Proposed metadata-only lifecycle_tombstones(id,resource_type,resource_id,actor_user_id,operation_id,deleted_at,counts_json); resource IDs unique by type and no FK to deleted rows. Retain indefinitely with audit, no content restore endpoint and no recovery promise. A future retention deadline is nullable metadata only until PM approves the exact policy/job. Product confirmation is separate from the assistant's authorization to perform destructive real-data actions; this blueprint performs none.

C7 — Shared attachment ownership contract for #47

Publish logical attachment_assets(id,storage_key,content_hash,byte_size,created_at) and card_attachment_refs(id,card_id,asset_id,display_name,created_at), unique ref IDs, nullable asset for validated external-link references. Asset IDs/storage paths never authorize reads. Every download/read checks the current card/board audience; no reusable public URL. Copy allocates new ref IDs with permission checks; moving refs changes access through their card, without fetching remote data.

Deletion removes only graph-owned refs. Asset bytes become eligible for separately implemented cleanup only after no live refs remain, a transactional eligibility check and storage-provider safety validation; no direct binary deletion here. Existing JSON/file/link entries require #47 inventory and migration without inventing blob ownership or claiming duplicates are safe. This contract is usable by #47 without waiting for all #41 implementation; attachment-dependent copy is deferred until that consumer is ready.

Error and event contract

New errors: {code,message,details?}. 400 INPUT_INVALID (safe field paths), 401 AUTHENTICATION_REQUIRED, 403 ACTION_FORBIDDEN for known readable resource/action, uniform 404 RESOURCE_UNAVAILABLE for missing or inaccessible source/destination, 409 REVISION_CONFLICT, PLAN_EXPIRED, PARENT_INACTIVE, MAPPING_REQUIRED, LABEL_LIMIT_EXCEEDED, ATTACHMENT_CONTRACT_UNAVAILABLE or OPERATION_KEY_CONFLICT; 413 PAYLOAD_TOO_LARGE; 500 OPERATION_FAILED with no SQL/internal paths. Denied/failed writes have no success audit/domain effects; safe denial audit remains allowed.

Audit actions include workspace/board close/reopen, board.template_update, collection create/update/delete/membership, list.presentation_update and content.copy/move/delete. Audit records actor, operation ID, source/destination scope, safe counts, revisions and mapping/drop summaries; omit card bodies, raw URLs and invitation/session tokens. Preserve existing audit names for unchanged endpoints. Exposing audit/history to readers follows current scoped access and D2, not a new global feed. #52 consumes authorized event metadata; #62 owns any future external delivery. This design guarantees at-most-once committed local effects per operation, not exactly-once network delivery.

U1 — Required web interaction states

Entry points: Management for workspace/board lifecycle, board menu for template/copy/transfer, list menu for presentation/copy/move/archive and card actions for configurable copy/transfer. Selectors show authorized active destinations only. Empty state distinguishes no eligible destination from no resources. Preview summarizes content/audience/mapping effects; unresolved mappings disable Confirm. Loading has named status; mutation disables repeated submission while keeping draft visible. Cancel/Escape before commit sends no mutation. After a lost response, retry uses the same operation key and queries the receipt; never creates a second copy.

Validation errors identify fields and preserve edits. Permission/session loss removes private source/destination content and redirects safely; transport error preserves draft and offers Retry. Modal uses existing dialog primitives, labelled headings/fields, trapped Tab/Shift+Tab, Escape and focus return; errors/status announce through live regions. At 320/768/1440 CSS pixels, headings/actions remain visible and selectors/impact rows scroll within the dialog. Color has a text name; collapse toggle exposes aria-expanded and count without requiring color/drag. Keyboard move/copy offers the same choices as pointer; preserve input/composition shortcut guards. Manual screen-reader and non-Chromium coverage must be reported explicitly.

7. Migration, failure recovery and rollback

  1. Before each approved schema slice, inventory current version, orphan parent/notification/default references, malformed JSON/duplicate IDs and label limits against synthetic rehearsal plus separately authorized target backup. Invalid legacy data blocks that slice; never silently drop or merge it.
  2. Use additive versioned/idempotent migrations matching existing schema conventions: active lifecycle defaults, zero revisions, no templates, empty collections/personal collapse/receipts/tombstones. Preserve all existing users, passwords, recovery keys, sessions, grants, memberships, audit, JSON content and personal/shared stars. Add indexes on parent/state/position, receipt unique key and effect key.
  3. Legacy list archives cannot reveal whether a child was independently archived. Backfill no guessed provenance. Restore list first, leave ambiguous archived children archived and explain the per-card restore action. This deliberate migration behavior requires D3 approval; no content is lost.
  4. Implement read/write effective-state guards before enabling close/template controls. Update session/bootstrap/navigation/search, auth preferences, existing mutation routes, scheduled automation and invitation acceptance together so no legacy bypass remains. Closing does not accidentally regenerate migration-derived memberships on startup; moving keeps #39 authority-loss triggers intact.
  5. For each transaction test fail after descendant insertion, parent update, mapping, event effect and audit. No receipt survives rollback. Retry deadlock/busy response with the same key only; unknown commit result uses receipt recovery. Never auto-retry a changed payload or conceal a stale preview.
  6. Old application versions do not enforce new lifecycle state. Once any resource is closed/template/provenance-managed, rollback must retain a compatible state-aware image or forward-fix. An older binary with additive columns is not automatically safe. Do not drop new columns or restore pre-revocation credentials/data. Permanent deletion cannot be undone by image rollback; data restoration requires separate authorization and a reviewed backup plan.
  7. Rehearse migration twice and restart with file-backed synthetic SQLite; compare graph counts/content hashes, foreign_key_check, integrity_check, #39 membership/invitation behavior and old API compatibility. Release only the committed reviewed candidate through required Canary/Production gates. No migration, deployment or data restoration is performed in this blueprint phase.

10. Product decisions before enabling new behavior

These recommendations distinguish policy choices from executable dependencies, as required by the Issue. They do not block completion or PM Testing of this blueprint, and are not claims of separately approved new disclosure or destructive behavior. Future implementation must follow its approved Issue scope; routine engineering choices require no repeated planning approval.

  1. D1 — Copy profile and template audience. Approve C3's conservative new-copy profile, no inherited people/history/rules, reset completion, opt-in dates/attachments and private templates. Keep source edit permission for card copy initially, matching current duplication; Observer-source copy is deferred. Keep legacy Duplicate unchanged. This diverges deliberately from Trello list copies that include comments.
  2. D2 — Audience changes across workspaces. Approve transfer only for administrators of both workspaces; preserve explicit board grants/membership and move content/history, warn about changed inherited audience, and revoke affected stale sessions/invitations. Require an explicit preview confirmation for cross-workspace board/list/card copy or move. Until approved, these actions are blocked.
  3. D3 — Archive and permanent deletion policy. Approve indefinite archive/close, no automatic purge, parent-first restore and conservative legacy archive provenance; metadata-only permanent tombstones/audits retained indefinitely. Permanent deletion requires archived/closed state plus fresh impact preview/typed confirmation by current scoped administrator. No recoverable trash period or automatic blob cleanup is introduced. Assistant execution against real data still needs applicable authorization.

Implementation order: begin with T1 archive/restore transaction plus audit rollback and recoverable client failure behavior when application implementation enters approved scope. It reuses existing endpoints, needs no schema change, and does not enable disclosure or permanent deletion. T1–T8 are future implementation dependencies, not unfinished blueprint acceptance criteria.
