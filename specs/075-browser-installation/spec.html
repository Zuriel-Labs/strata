Browser installation

Approved scope: Issue #75. Baseline: 64736bb5dd7b0b69fd3011d8172cc354d18116cc.

Objective and success criteria

Users of supporting browsers can install Strata through the browser, recognize its icon, and reopen it in a standalone window. Existing tab use, login, logout, authorization and Board workflows continue to work.

  • The document links a valid same-origin manifest. Manifest identity, scope and launch URL are /; display mode is standalone.
  • The app name is Strata. Real PNG assets include 192×192 and 512×512 install icons and a 180×180 Apple touch icon. A full-bleed background and centered layers keep the maskable artwork safe.
  • Assets work anonymously through the production Express static handler with the existing security headers. Missing assets remain 404, never the SPA document.
  • Desktop Chrome/Edge installation, close/relaunch and uninstall are verified where those browsers are available. Actual mobile-device installation is explicitly marked unverified when unavailable; viewport emulation is not installation proof.

Evidence and architecture

The baseline index.html has no manifest link. Vite already copies a public/ directory into dist/, and server/src/app.ts serves that directory before the SPA fallback. The Dockerfile copies dist/ into the runtime image. No API, RBAC, audit or schema changes are needed.

MDN installation guidance documents manifest metadata, HTTPS, browser differences and standalone display. Service workers are optional for installation. Use static files and native installation; add no service worker, offline cache, dependency or custom install prompt.

Use the existing navy and blue/purple theme from src/index.css and AuthScreen.tsx. The new icon is an original geometric stack of three layers; its SVG is the editable master.

Structure and style

  • index.html: manifest, icon and theme metadata.
  • public/manifest.webmanifest and public/icons/: deployable metadata and original artwork.
  • src/installability.test.ts: source manifest and asset regression test.
  • tests/e2e/installability.spec.ts: real-browser parsing, image decoding and normal tab behavior.
  • docs/installing-strata.html: installation, launch, removal and browser limits.

Follow existing indented HTML and JSON; tests use explicit TypeScript and named imports.

Plan and ordered tasks

  1. Write one source regression test, run it RED, add the manifest, links and icons, then prove GREEN. Acceptance: required metadata and actual PNG dimensions are valid.
  2. Add browser coverage and installation guidance. Acceptance: the browser parses the manifest and decodes its icons without breaking ordinary tab use. Verify production static serving and security headers during local QA.
  3. Run the complete local checks, review the diff, commit the exact candidate, open the PR and deploy Canary through the existing pipeline. Acceptance: exact source/image/configuration evidence and numbered PM testing steps, with unavailable browser/device checks stated explicitly.

Dependency order: manifest and icons precede browser checks; local gates and committed source precede image publication; healthy Canary precedes In Review. Risks: invalid icon metadata, SPA fallback hiding missing assets, browser-specific installation limits. Mitigate through binary/image checks, real requests and explicit test coverage limits.

Boundaries and rollback

  • Always preserve authentication, RBAC, audit, CSP and data. Installation requires the same access as normal web use.
  • Separate exact-candidate approval is required for merge and Production. No native wrapper, app store, push notifications or offline editing is authorized by this Issue.
  • No migration or user-data mutation is part of the change. Rollback restores the previous GitOps image digest; no database rollback is needed.

No unresolved product decision is required before implementation. Canary installation verification and actual device/browser availability remain runtime evidence to collect, not assumptions.
