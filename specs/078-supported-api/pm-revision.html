API key and service account review

PM feedback on PR 79 at 1032a8d: the account panel mixes creation, approved app management, and client registration; the numeric expiry field cannot be cleared; broad scopes obscure available actions. The current API already stores multiple grants and shares an explicit route catalog with OpenAPI.

Acceptance

  1. API Connections opens the generator at Name. Resources and Permissions follow. Expiry is a native select (1, 7, 30, 60, 90, 180 days; default 7). Review shows the choices before issuance. Focus moves with the step. Back preserves selections. The secret appears once. Copy API key writes it to the clipboard on request and confirms success; if clipboard access is blocked, the wizard selects the key for manual copying.
  2. API Keys shows one row per key and filters by name. Tap or activate the row to show access details. Active keys alone have a trash icon; activating it changes it to a red question mark. Activate again to revoke. Escape or opening a row cancels confirmation. Create API key and New service account are visibly styled buttons. The reference link reads API Docs. Approved Apps has its own screen, including interactive client registration. A save error stays with the failed operation.
  3. Permissions derive from the existing operation catalog and current resource roles. No permission is preselected. Server issuance and every request enforce the action allowlist, resource bounds, and live roles. Existing OAuth scope contracts and legacy keys remain compatible. New keys have a separate prefix so a rollback cannot interpret their action permissions as broader legacy scopes.
  4. Admin Service Accounts have a stable ID and unique username, separate from their owner. They can join workspaces and boards, appear as board members for card and automation assignments, and act under their own ID on existing API routes. They cannot sign in with a browser or use personal account actions.
  5. Workspace and board assignments persist independently of keys. A key limits the service account's assigned resources and actions. Effective access is capped by the live owner and by the authority approved at issuance. Only the owner can issue keys or transfer ownership. Transfer keeps the identity, narrows assignments to the recipient's authority, revokes the prior key, and requires explicit reissuance. Disabled owners cannot authorize requests.
  6. Select all shown and Clear shown affect only permissions matching the current search and access level filter. Hidden selections stay as they are.
  7. Role presets are offered for access levels available on every selected resource. Choosing a preset replaces the selection with all eligible actions at that level and below, including individual actions on shared endpoints. Account permissions form a separate preset. A preset resets filters so the full selection can be inspected. Manual edits or resource changes return the control to Custom; resource changes remove unavailable permissions without adding new ones. Review remains required. A preset is a selection shortcut and does not change anyone's role.

Verification

Test compatibility, all six expiries, multiple keys, per-action access, scope and role reductions, service account ownership and transfers, and safe attribution. Exercise narrow and desktop layouts, keyboard flow, errors, back navigation, one-time secrets and distinct management screens. Replace the previously reviewed candidate only after exact CI and Canary checks.
