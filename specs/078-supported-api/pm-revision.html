API key and service account review

PM feedback on PR 79 at 1032a8d: the account panel mixes creation, approved app management, and client registration; the numeric expiry field cannot be cleared; broad scopes obscure available actions. The current API already stores multiple grants and shares an explicit route catalog with OpenAPI.

Acceptance

  1. API Connections opens the generator at Name. Resources and Permissions follow. Expiry is a native select (1, 7, 30, 60, 90, 180 days; default 7). Review shows the choices before issuance. Focus moves with the step. Back preserves selections. The secret appears once.
  2. API Keys lists multiple named keys, with status, access details, expiry, last use, and revocation. Approved Apps has its own screen, including interactive client registration. A save error stays with the failed operation.
  3. Permissions derive from the existing operation catalog and current resource roles. No permission is preselected. Server issuance and every request enforce the action allowlist, resource bounds, and live roles. Existing OAuth scope contracts and legacy keys remain compatible. New keys have a separate prefix so a rollback cannot interpret their action permissions as broader legacy scopes.
  4. Admin Service Accounts use the same wizard. Unique agent names, owner-only management, named audit attribution, and no personal account actions. Service accounts use existing API routes. Ownership transfer revokes the previous credential and retains only the overlap of existing access and the recipient's current authority. A new key requires explicit issuance. Disabled owners and lost administrative access cannot authorize requests.
  5. Select all shown and Clear shown affect only permissions matching the current search and access level filter. Hidden selections stay as they are.
  6. Role presets are offered for access levels available on every selected resource. Choosing a preset replaces the selection with all eligible actions at that level and below, including individual actions on shared endpoints. Account permissions form a separate preset. A preset resets filters so the full selection can be inspected. Manual edits or resource changes return the control to Custom; resource changes remove unavailable permissions without adding new ones. Review remains required. A preset is a selection shortcut and does not change anyone's role.

Verification

Test compatibility, all six expiries, multiple keys, per-action access, scope and role reductions, service account ownership and transfers, and safe attribution. Exercise narrow and desktop layouts, keyboard flow, errors, back navigation, one-time secrets and distinct management screens. Replace the previously reviewed candidate only after exact CI and Canary checks.
