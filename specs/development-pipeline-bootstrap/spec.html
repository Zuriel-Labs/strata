Strata Development Pipeline Bootstrap

Adopt Versa’s one-active-Issue, agent-managed, Canary-to-Production development model while preserving Strata’s Express/Vite architecture, SQLite data safety, Discord coordination, existing issue forms, and GitOps topology.

Source baseline: Zuriel-Labs/strata origin/main Reference: Zuriel-Labs/versa main Status: proposed Production: explicitly out of scope until approval

Assumptions requiring PM review

  1. Dedicated Project: create a private Zuriel-Labs organization Project titled Strata, separate from the legacy Broville Roadmap, because this is the closest match to Versa’s live structure and avoids mixing the one-active-Issue invariant with other Broville products.
  2. Historical migration: add every existing Strata Issue to the dedicated Project as Done, preserving Issue state and labels. Do not invent missing historical Impact or Effort. After readback proves the new Project is complete, remove only the duplicate Strata cards from Broville Roadmap; do not alter other projects or Issues.
  3. Bootstrap record: create one approved maintenance Issue for this adoption, make it the sole In Progress item, and deliver the bootstrap through its own branch, PR, local QA, CI, immutable Canary image, and PM Canary review.
  4. Approval transport: preserve Strata’s existing Discord governance. The exact candidate-specific phrase Approved to merge and deploy production must be attributable to the PM through the Strata Discord/Issue synchronization record before merge or Production promotion.
  5. No branch protection: do not create a repository or organization ruleset and do not add classic branch protection. Strata has one active developer, so the workflow will use squash-only merge settings, automatic merged-branch deletion, CI evidence, policy, and pipeline audits without a server-enforced PR gate.

Decision gate: implementation must not begin until the PM approves these assumptions or supplies corrections.

Objective and observable outcome

Make Strata’s development workflow deterministic across Codex, Claude, Gemini, OpenCode-compatible agents, GitHub, Zot, Gitea, Argo CD, Canary, and Production. The PM selects work and approves exact candidates; agents own metadata transitions, implementation, review, release mechanics, verification, rollback, and readback.

Acceptance criteria

  • One canonical AGENTS.md describes the Strata-specific pipeline without stale Versa names or Next.js assumptions.
  • CLAUDE.md and GEMINI.md import AGENTS.md; they do not duplicate policy.
  • Nine strata-* workflow skills, five shared frontend skills, regular-file Claude adapters, and deterministic alignment scripts are repository-owned and validated.
  • The private Strata Project has the exact governed fields and views, contains every Strata Issue, and has no more than one active Issue.
  • Issue, Project, label, assignee, branch, PR, CI, candidate, Canary, Production, and completion states remain synchronized and auditable.
  • The CI job is consistently named Quality / verify and runs the repository skill check plus Strata’s complete application gates.
  • Canary is built once from an exact clean committed archive for linux/amd64, pinned by Zot digest through Gitea/Argo CD, and verified before PM review.
  • Production reuses the exact approved Canary digest, preserves the NFS-backed SQLite database and backup system, and rolls back non-destructively on deployment failure.
  • No user-owned checkout changes, runtime SQLite data, secrets, unrelated Project cards, or unrelated homelab changes are overwritten or committed.

Workflow contract

  1. Create: research duplicates, show the complete HTML Issue and metadata, receive exact-draft approval, create it in Backlog, populate governed fields, and read everything back.
  2. Select: PM selects work; agent verifies the active slot is empty, moves the Issue to In Progress, assigns only brimdor, and reads back the transition.
  3. Implement: use an isolated worktree from current origin/main, Red → Green → Refactor, focused commits, full local gates, and a PR with Refs #N.
  4. Agent review: independently inspect correctness, security, RBAC, audit, validation, SQLite compatibility, UX/accessibility, responsive behavior, and operations; run hands-on local browser tests; remediate all findings.
  5. Canary: require Quality / verify for the exact PR head; build once from an exact archive; push to Zot; update only apps/strata-canary/values.yaml; verify exact digest and all-green; then move to In Review.
  6. PM review: provide numbered, change-specific Canary steps and the exact approval phrase in its own copyable code block. Findings move the Issue back to In Progress and invalidate the candidate.
  7. Close: after exact approval, squash-merge; prove the merged tree equals the approved PR tree; promote the approved digest without rebuild; verify Production and storage; clean only unreferenced Strata image manifests; close the Issue and move it to Done.

Testing strategy

  • Pipeline unit tests: temporary fixture repositories exercise alignment, adapter, candidate, and Project-audit scripts without mutating GitHub.
  • Negative cases: two active Issues, missing metadata, stale Project title, auto-close PR text, wrong check name, wrong digest, wrong chart target, dirty source, mismatched tree, multiple/missing image pins, and unsafe Production rebuild all fail closed.
  • Skill validation: run the current bundled skill validator on all nine adapted workflow packages and five shared packages; run alignment and realistic routing checks.
  • Application regression: npm run check, including typecheck, lint, Vitest, build, and Playwright E2E.
  • GitHub readback: Project identity, field options, views, Issue/card metadata, one-active count, repository merge settings, PR linkage, and CI result.
  • Canary runtime: exact digest, Argo revision/sync/health, pod readiness/restarts, /api/health, logs/events, external TLS/route, and whole-cluster health.
  • Production runtime: all Canary-grade checks plus pre/post SQLite integrity, data counts/sanity, PVC identity, backup freshness/success, and rollback target.

Boundaries

Always

  • Read live Issue, Project, PR, CI, Git, registry, homelab, and runtime state immediately before dependent action.
  • Use isolated worktrees and exact committed archives; preserve unknown user-owned changes.
  • Perform and read back agent-owned metadata transitions; provide numbered PM testing steps.
  • Keep durable deployment changes in homelab Gitea master and let Argo CD reconcile.

Ask first

  • Create a GitHub Issue from a proposed draft; change a candidate after approval; add dependencies; perform destructive schema/data recovery; change Discord approval authority; or expand beyond Strata.

Never

  • Deploy Production without the exact current-candidate approval; rebuild for Production; close on merge alone; bypass auth/RBAC/audit/CI; expose secrets; use a Kubernetes node as a build host; delete a referenced image; or overwrite runtime/user-owned data.

Known gaps found during research

  1. Versa reference drift: the live Project is titled Versa, while Versa’s checked-in health script expects Versa Development; npm run pipeline:health currently fails. Strata will use one discovered/canonical title and test this condition.
  2. Intentionally unprotected Strata main: Strata currently permits squash, merge commits, and rebase merges; automatic branch deletion is off. Per PM direction, the bootstrap will make merging squash-only and enable automatic branch deletion, but will not create branch protection or a ruleset.
  3. Project drift: the shared Roadmap has different Status/Priority names, no Impact field, and stale closed Strata cards in Backlog.
  4. Repository drift: the primary local checkout is one commit ahead, nineteen commits behind, and has a user-owned AGENTS.md edit. Implementation must remain in the isolated clean worktree and reconcile the useful local policy without touching that checkout.
  5. CI mismatch: current Strata CI is named CI / test, runs Node 20/actions v4, and does not validate repository skills; the Dockerfile uses Node 22.
  6. Missing portability layer: Strata has no canonical repo-local skills, Claude adapters, Gemini import, shared policy, alignment audit, candidate check, or pipeline-health command.
  7. Release verifier mismatch: Versa’s verifier assumes one pod with migrate/web/worker; Strata needs one main container plus SQLite/PVC/backup checks.
  8. External feedback access: Zuriel-Labs currently has no spare paid seat, and GitHub provides no Issues-only permission for a private source repository. doreliz will not be added during this bootstrap; a separate feedback channel is deferred.

Non-goals

  • No product feature, API, schema, UI, authentication, RBAC, or runtime-data change.
  • No Production deployment or merge before exact candidate approval.
  • No mass deletion of legacy labels or historical Issue metadata.
  • No modification of unrelated Broville Roadmap cards or homelab applications.
  • No branch protection or repository ruleset.
  • No paid seat or repository access for doreliz.
  • No attempt to imitate Versa’s Next.js/PostgreSQL runtime topology.
